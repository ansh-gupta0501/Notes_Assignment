- Second way to decouple our application 

- What if you want to send one message to many receivers?
- We can go the route of **direct integration**, for example, having a buying service sending an email notification , then talking to a fraud service, talking to shipping service, and talking to the SQS queue. But this will be quite complicated because we need to write these 4 direct integrations
- Instead , we can use something called a **Pub/Sub** type of integration, in which we have an SNS topic. The buying service will be sending a message into our SNS topic and the topic automatically will be smart enough to send a notification via email to the fraud service, to the shipping service, and even to the SQS Queue

- SNS stands for **Simple Notification Service**
- The **event publishers** will only send messages to one SNS topic
- You can have as many **event subscribers** as you want to listen to the SNS topic notifications
- Each subsciber to the topic will get all the messages so this is different form SQS where the consumers were sharing the messages.
- In this example , each subsciber to the topic will get all the messages send to the SNS topic
- Each SNS topic can have more than 12 million subscriptions per topic and also we have a soft limit of 100,000 topics limits for each account
- So SNS has many destinations , it can publish to many subscribers and from the AWS target service from SNS we have SQS, Lambda, amazon data firehose. But also we can send emails, directly from SNS, we can send SMS and mobile notifications and also we can send data directly into a HTTP or HTTP(S) endpoint

# Amazon SNS overview and industry use

SNS is a pub/sub messaging service that lets one publisher fan out events to many independent subscribers. It’s commonly used to decouple producers from multiple downstream systems that all need the same event, in near real time.

---

## Core concepts

- **Publisher (producer):** Sends a message once to an **SNS topic**.
- **Topic:** Logical channel that receives messages and fans them out to all subscribers.
- **Subscriber (consumer):** Any endpoint that receives every message from the topic (SQS queues, Lambda, HTTP(S) endpoints, email, SMS, mobile push, Firehose).
- **Fan‑out:** One message → delivered to many subscribers in parallel.
- **Protocols:** HTTP/HTTPS, email, SMS, mobile push, AWS services (Lambda, SQS, Firehose).

---

## How SNS works

- **Publish:** Your app calls `Publish` with a small payload (often JSON).  
- **Delivery:** SNS pushes that message to all subscribed endpoints.  
- **Retries:** For push protocols (HTTP/S, Lambda), SNS retries with backoff on transient failures.  
- **Filtering:** Subscribers can define **message attribute filters** to receive only relevant events.  
- **Security:** Topic policies control who can publish and subscribe; per‑protocol authentication applies (e.g., HTTPS signatures, IAM).

---

## How SNS is different from SQS

| Aspect | SNS (Pub/Sub fan‑out) | SQS (Queue + polling) |
|---|---|---|
| **Pattern** | Publish once, deliver to many | Produce to a queue, consumed by workers |
| **Delivery** | Push to subscribers | Pull/long‑poll by consumers |
| **Message sharing** | Every subscriber gets the message | Messages are shared among consumers of the same queue |
| **Use cases** | Notifications, broadcast events, multi‑system triggers | Work distribution, buffering, backpressure handling |
| **Ordering/duplicates** | Depends on protocol; FIFO topics available | Standard: at‑least‑once, best‑effort ordering; FIFO: ordered, dedup |
| **Fan‑out** | Native (one → many) | Requires SNS→SQS integration or multiple queues |

## Industry examples

- **E‑commerce order events:**  
  - **Publisher:** Checkout service publishes “OrderPlaced” to SNS.  
  - **Subscribers:**  
    - **SQS (Shipping workers):** Process fulfillment asynchronously.  
    - **Lambda (Fraud check):** Immediate risk scoring.  
    - **HTTP(S) (ERP):** Update external inventory system.  
    - **Email/SMS:** Customer confirmation.  
    - **Firehose:** Archive events to S3/Redshift for analytics.  
  - **Benefit:** One publish triggers all downstream systems without custom point‑to‑point integrations.

- **Operational alerts and observability:**  
  - **Publisher:** CloudWatch Alarms or monitoring agents.  
  - **Subscribers:**  
    - **Email/SMS:** On‑call notifications.  
    - **Lambda:** Auto‑remediation (e.g., restart service).  
    - **HTTP(S)/ChatOps:** Post to Slack/MS Teams.  
  - **Benefit:** Central alerting that fans out to people and automation.

- **Content pipelines and media:**  
  - **Publisher:** “UploadCompleted” from a web app.  
  - **Subscribers:**  
    - **Lambda:** Validate metadata.  
    - **SQS:** Transcoding job queue.  
    - **Firehose:** Analytics lake in S3.  
  - **Benefit:** Parallel post‑upload workflows kicked off instantly.

- **IoT and device events:**  
  - **Publisher:** Gateways publish device telemetry or alarms.  
  - **Subscribers:**  
    - **Lambda:** Real‑time rule evaluation.  
    - **SQS:** Batch processing workers.  
    - **Open endpoints:** Partner systems via HTTPS.  
  - **Benefit:** Broadcast device events to multiple teams/systems at once.

## Design patterns and best practices

- **Fan‑out to SQS queues:**  
  - **Pattern:** SNS topic → multiple SQS queues (one per downstream team or service).  
  - **Benefit:** Each team scales and processes independently, with retry/DLQ control at the queue.

- **Message filtering:**  
  - **Pattern:** Add attributes (e.g., `eventType=OrderPlaced`, `priority=HIGH`) and configure subscriber filters.  
  - **Benefit:** Reduce noise; each subscriber receives only relevant messages.

- **Dead‑letter handling:**  
  - **Pattern:** For Lambda or SQS subscribers, configure DLQs to capture failed deliveries/processing.  
  - **Benefit:** Debug poison messages without blocking the main flow.

- **Security and governance:**  
  - **Pattern:** Topic policies limit who can publish/subscribe; use per‑subscriber credentials and HTTPS with signature validation for webhooks.  
  - **Benefit:** Prevent unauthorized spam or data leaks.

- **Payload design:**  
  - **Pattern:** Use compact JSON with a **stable schema** and a **version field**; include a unique event ID and timestamp.  
  - **Benefit:** Easier evolution and idempotent processing downstream.

- **Choosing FIFO topics:**  
  - **Pattern:** When order and dedup are critical across subscribers (e.g., price updates, ledger events), use **SNS FIFO topics** with **SQS FIFO** subscribers.  
  - **Benefit:** Guaranteed per‑group ordering end‑to‑end.

---

## Simple takeaway

- **SNS**: Publish once, notify many. Great for broadcasting events to multiple systems and humans, in near real time.  
- **SQS**: Queue work for workers to pull and process at their pace. Great for buffering, scaling, and resilience.  
- Combine them for robust architectures: **SNS (event fan‑out) → SQS (per‑service queues)** → workers, plus **Lambda/HTTP(S)** for immediate reactions.
