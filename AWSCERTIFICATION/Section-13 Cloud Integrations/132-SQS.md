# Amazon SQS - Simple Queue Service 

## What's a queue?
- We are creating an SQS queue 
- What we enable us to do to have **producers** send messages into that queue, and then it could be one producer but it could be as well , multiple producers
- And once the messages are stored in the queue, then they could be read by **consumers** who will be polling the queue that means requesting messages from the queue and it could be one consumer or multiple consumers
- Once the consumer poll messages, they will share the work so each consumer will get a different messages and when they're done processing a message ,for example, to process a video then they will delete the message from the queue and it will be gone.
- So in this mechanism, we have the producers sending messages into the queue and they are decoupled from the consumer reading the messages from the queue and processing them at different speed.

```

        Producer                                Consumer
                \    Send             Poll      /
                 \  messages          messages /
        Producer ---------> SQS Queue ---------> Consumer
                 /                             \
                /                               \
        Producer                                  Consumer
        
```

# Amazon SQS - Standard Queue
- When you have SQS, it is the AWS oldest offering (over 10 years old)
- It is fully managed, it's a serverless service , you don't provision servers
- It is used to decouple applications
- It will scale seamlessly from one message per second to 10000s of messages per second
- The default retention of the messages if 4 days , maximum of 14 days. So you need to process them within that default retention
- There is no limit to how many messages can be in a queue
- Once the consumers read the messages then they have to be deleted
- There is low latency (less than 10 milliseconds, on publish and subscribe/receive)
- Consumers share the work to read messages and scale horizontally

## SQS to decouple between application tiers
- We have our web servers and they are making request maybe through an application load balancer. They are served through an EC2 instances in an auto scaling group. And then , for example, say that our users want us to process some videos, then instead of sending it directly to the video application , we can instead insert messages into an SQS queue and then we will have a video processing layer made of an auto scaling group with EC2 instances and these EC2 instances , will be reading from the SQS queue and processing our videos
- Now we can scale the second auto scaling group independently from the first one and this is why it's called decoupling. And on top of it , the scaling can happen based on how many messages there are in the SQS queue
- This will really allow us to have two layers, the web servers and the video processing fully decoupled from the SQS queue and scaling independently

```

                Web Servers                                             Video Processing
 
    Requests                        Put
  ------------> EC2 Instances ----------------> SNS Queue -------------------> EC2 Instances
                Auto Scaling group                                              Auto Scaling Group
```


# Amazon SQS - FIFO Queue
- FIFO means First In First Out, and that corresponds to the ordering of the messages within the queue
- So if you have a producer sending messages in a specific order such as 1,2,3,4 then the consumer will also read these messages in order
- When you have a normal SQS queue, consumer can read messages altogther and they could be in different orders. But with Amazon SQS FIFO queues, the messages are going to be in order
```
                Send messages                                   Poll messages
Producer -------------------------------> SQS FIFO Queue --------------------> Consumer
            4   3   2    1                                  4    3    2    1
```
